# 规则成熟度与 Linter 路线

AI 可消费 case 的规则不应该永远停留在文档里。成熟后，一部分规则可以自动检查，一部分规则保留给人工判断，一部分规则留给公司自定义。

## 规则成熟度

### Must

不满足就不能输出。

典型规则：

- 不可编造
- 不可占位
- 单线瀑布
- 唯一断言
- 信息缺口必反问
- UI 元素必须有证据
- 异常注入必须写到工具和路径

这些规则适合进入 linter，至少做文本级拦截。

### Should

强烈建议遵守，但允许团队根据执行器能力调整。

典型规则：

- 默认冷启动
- emoji 剥离
- 颜色加容差注释
- 尽量使用主动动作替代被动等待
- 反例驱动更新规则

这些规则适合做 warning。

### Team-specific

必须由团队自己定义。

典型规则：

- 输出 8 级层级还是表格
- feature list / PRD 格式
- 公司测试账号管理方式
- 内部造数工具
- 内部异常注入工具
- AI PHONE / 其他执行器的自动化边界

这些规则不适合硬编码进公开版。

## Linter 路线

第一版 linter 可以先做文本检查，不需要理解完整业务。

### P0：明显不可消费

- 扫占位词：`测试账号`、`某页面`、`若干`、`XXX`、`待定`
- 扫业务分支：`如果`、`若不存在`、`找不到`、`按相同规则`、`重复以上`
- 扫抽象动作：`进入页面`、`查看`、`完成操作`、`正常处理`
- 扫多断言：预期结果中出现多个独立分号或多个观察对象
- 扫异常占位：`网络异常`、`接口失败`、`已断网` 但没有工具路径

### P1：质量风险

- 前置条件中出现业务导航路径
- 前置条件中出现资源状态
- 操作步骤中缺少控件文案
- 预期结果中出现“成功 / 正常 / 正确”但没有视觉证据
- 颜色词后缺少 `（颜色仅参考）`
- case 字段中出现 emoji

### P2：结构一致性

- `.txt` 与 `.md` case 数量不一致
- 标题 / 前置 / 步骤 / 预期字段缺失
- 层级数量不符合团队定义
- 场景标签不在允许集合内
- 【人工】标签位置错误

## 推荐输出

linter 不要只报错，也要给改写方向。

示例：

```text
ERROR case-003 操作步骤包含“找不到则换下一个”
原因：业务决策分支会让执行器在运行时做选择。
建议：改为具名资源，或在步骤中保留 1 个同质筛选并提供后置定位手段。
```

## 不急着自动化的部分

以下内容仍适合人工或 AI review：

- UI 元素是否真的来自 spec / 截图
- 资源筛选是否同质
- 断言是否跨业务对象
- 某个 case 是否应该人工路由
- 一条规则是否应该从 Should 升级成 Must
