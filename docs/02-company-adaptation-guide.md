# 公司适配指南

公开版 `skills/spec-to-testcase` 不能原样替代公司的测试规范。它更像一套起点：先把“AI 可消费 case”的骨架立住，再把业务真值、环境真值、执行器边界补进去。

## 必须替换的内容

1. Feature list 格式

   明确模块、功能点、业务规则、异常处理、交互说明、验收项如何书写。如果公司已有 PRD 模板，应先把模板映射到 skill 的解析规则。

2. 测试入口

   明确 App 包名、Web 域名、小程序入口、登录路径、首页结构、常见弹窗处理策略。

3. 测试账号

   不写“测试账号”。要给具体账号、密码、身份、权限、灰度命中方式。敏感信息不要进开源仓库，可在内部补充文件或运行时上下文中提供。

4. 测试数据构造

   明确数据来自后台按钮、SQL、接口、fixture、Mock 服务还是执行步骤本身。不能只写“已有数据”。

5. 异常注入

   明确网络错误、接口错误、权限错误、空数据、超时等异常怎么造。比如飞行模式、网络代理、Debug 菜单、后端开关、测试数据后台。

6. UI 证据来源

   明确 UI 控件文案、位置、弹窗结构来自 feature list、截图、设计稿、录屏还是用户答复。不能靠模型视觉想象。

7. 执行器能力边界

   明确哪些动作 AI PHONE 或其他执行器可以自动做，哪些必须人工路由。比如真实支付、真实 GPS、指纹、人脸、跨设备协作、长时间等待。

## 推荐落地步骤

1. 先用 3 到 5 条真实业务 case 做 before / after 对照。
2. 把执行失败原因分成三类：写法问题、信息缺口、执行器边界。
3. 每次失败只把可复用规则沉淀进 skill，不把偶发业务细节硬编码成铁律。
4. 每个迭代保留“为什么这条规则存在”的反例，避免团队后续把规则改软。
5. 用 AI PHONE 或其他执行器跑一轮真实闭环，再调整人工路由规则。

## 开源边界

开源仓库只保留方法论、Demo 示例和可替换模板。公司内部版可以在此基础上增加：

- 内部 feature list 模板
- 内部账号与环境说明
- 内部造数工具
- 内部异常注入工具
- 特定产品 UI 规则
- 历史失败案例复盘
