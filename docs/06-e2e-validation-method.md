# 端到端验证方法

AI 可消费 case 规则不应该只靠经验推导。更可靠的方式是：写出 case，交给真实执行器跑，记录失败，再把失败原因反哺回规则。

这个过程适用于 AI PHONE，也适用于其他 App / Web 视觉执行器。

## 闭环流程

```text
feature list / PRD
  -> baseline skill 生成 case
  -> 投递给执行器
  -> 获取执行日志
  -> 归因失败原因
  -> 修改 rules / questionnaire / routing
  -> 重跑验证
```

## 六条实验约定

### M1：单因子实验

每轮只改一个维度，例如标题写法、前置条件、步骤粒度、预期断言数、资源筛选方式。

如果一轮同时改了多个维度，即使结果变好，也很难知道是哪一个变化起作用。

### M2：正反对照

每条重要规则最好同时保留正例和反例。

正例证明“这样能跑”，反例证明“为什么必须禁止那样写”。开源读者往往更容易从反例理解规则价值。

### M3：实测数据驱动

判断一条规则是否有效，不只看最终成功或失败，还应看：

- 执行步数
- 执行耗时
- 执行器思考过程
- 最终判定摘要
- 是否出现假设、猜测、循环、卡住

执行成功不代表规则可以删。它可能只是这条 case 碰巧简单。

### M4：批次化研究

一次围绕一个研究问题跑一批 5 到 10 条。批次结束后先写小结，再开下一批。

不要让随机发现持续打断主线，否则规则会越来越散。

### M5：每轮必记 5 元素

每轮至少记录：

- 研究问题：这轮想验证什么
- 变量：和基线相比改了什么
- Run content：实际投递给执行器的 case 原文
- 执行轨迹：关键步骤、卡点、执行器思考摘要
- Finding：这轮得到了什么发现

缺少 run content 的记录不可复盘；缺少 finding 的记录不可反哺。

### M6：反哺链路可追溯

每条规则改动都应该能追溯到某次执行、某条 case、某个失败或成功现象。

推荐记录格式：

```text
R-012 / case: demo-login-003
现象：执行器在步骤 4 出现“假设当前位于登录页”
归因：前置条件声明了页面状态，但步骤没有给出入口路径
反哺：ai-executable-rules.md 增加“路径吞掉 → 跳转露出”对照
复验：R-013 同 case 通过
```

## 失败归因

建议把失败分成三类，不要全部归给模型。

| 类型 | 典型现象 | 应该反哺到 |
|------|----------|------------|
| 写法问题 | 多断言、分支步骤、前置塞业务事实、抽象动作 | `ai-executable-rules.md` |
| 信息缺口 | 缺账号、缺入口路径、缺 UI 文案、缺异常注入方式 | `execution-context-questionnaire.md` |
| 执行器边界 | 真实支付、真实 GPS、跨设备、硬件交互、超长流程 | `manual-case-rules.md` |

## 适用边界

这套方法适合：

- 中长期维护的功能模块
- 有真实执行环境
- feature list / PRD 相对稳定
- 团队愿意持续维护 rules

不太适合：

- 只有几条 case 的一次性项目
- 没有真实执行器反馈的纯文档项目
- UI 每几天大改的早期探索项目
- 当天必须交付、没有迭代时间的任务

## 最小起步

建议第一批只跑 5 条：

1. 启动 App 并看到首页。
2. 正向主流程。
3. 反向取消流程。
4. 一个异常注入流程。
5. 一个故意写坏的反例 case。

第五条很重要。一个健康的规则体系，应该能明确拒绝不可消费输入，而不是为了“生成结果”编造缺口。
