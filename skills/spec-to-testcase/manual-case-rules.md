# 人工 case 判定规范

> 本文规定：Phase 4.5 总检阶段如何判定一条 case 必须由人工执行，并打 `【人工】` 路由标签。
> 与 [ai-executable-rules.md](ai-executable-rules.md)（写法层）+ [execution-context-questionnaire.md](execution-context-questionnaire.md)（信息层）并列——前两门管「case 应不应该生成」，本文管「生成出来 VLM 能不能跑」，**两个独立维度，互不让步**。

---

## 准出铁律（不可妥协）

- **step-first 路由原则**：任何【人工】判定前先做反问——「这个状态能否由 case 步骤路径触发到位？」能 → 步骤里完整构造、不打【人工】；不能 → 才进入 6 类边界判定。**【人工】判定来源仅限下文 6 类边界 + 「非人工判定理由」清单双重通过**——清单外的"预置便利 / 流程稍长（< 60 步）/ UI 推测 / 状态构造繁琐 / 缺示例 / 缺截图"等一律不构成人工依据
- **写作阶段不预判**：所有 case 一律按 VLM 可执行写作；执行方式判定全部留给 Phase 4.5 总检
- **先反问能否改自动**：命中下述 6 类边界时，先反问用户「能否改写为 VLM 可执行的等价版本？」——能改不打、改不了才打
- **【人工】是路由标签，不是豁免口**：打了【人工】也不放宽任何写法 / 信息层铁律，case 内容仍按全套铁律生成
- **标签位置固定**：`【人工】` 永远放在场景标签**前面**

**未按上述铁律打/不打标签的 case 即为不合格，禁止输出。**

---

## VLM 边界判定（6 类）

case 命中任一类即触发反问、判定后打 `【人工】`：

| # | 类别 | 触发例 |
|---|------|------|
| 1 | **跨端 / 跨系统** | 测前需在管理后台创建资源 / 跨设备协同（A 发 B 收）/ 第三方 OAuth / 真实支付 / 改后台配置后回 App 验证 |
| 2 | **流程超长** | 步骤数 ≥ 约 60 步 |
| 3 | **前置链条超复杂** | 多账号多角色组合（A 准备 + B 操作 + C 验证）/ 多资源依赖链（建 X → 关联 Y → 触发 Z）/ 依赖后端定时任务执行 |
| 4 | **判断高难度** | 公式 / 数学计算 / 大量数值推导（"列表前 5 项总数应为 X"）/ 跨页面信息汇总 / 历史状态对比 |
| 5 | **真实环境敏感** | 真实时间窗口（7 天后）/ 真实 GPS / 真实人脸 / 指纹 / 声纹 / 实时音视频 / 真实第三方短信 / 真实弱网 QoS（持续低速、丢包；可 mock 的开关型异常如飞行模式 / Charles 归信号 7 异常注入工具） |
| 6 | **硬件交互** | NFC / 蓝牙 / 音量键 / 震动 / 重力感应 |

## 非人工判定理由（反捷径清单）

下列理由 **不构成** 【人工】打标依据；命中即应回滚为 VLM case 并把构造路径完整收拢到步骤里。

| # | 误判理由 | 正确做法 |
|---|---------|---------|
| 1 | "目标状态预置成本高" | 步骤里完整构造（拖进度条 / 完成 N 题 / 切 Tab 切学段等） |
| 2 | "步骤会变长" | < 60 步即合规，按 [ai-executable-rules.md](ai-executable-rules.md) 完整写步骤 |
| 3 | "UI 元素 spec 没写、需推测" | 触发 [execution-context-questionnaire.md](execution-context-questionnaire.md) 反问，反问能解决就走信息层 |
| 4 | "需要先达到 X 状态（视频 100% / 题已完成 / 已学过）" | 步骤里完整走"看完视频 / 完成全部题 / 先操作一遍触发状态"路径 |
| 5 | "需要找回刚操作的资源" | 用 [ai-executable-rules.md](ai-executable-rules.md) 第 13 条同质筛选 + 后置反向定位 |
| 6 | "弹窗内容 / 入口位置 / 控件文案 spec 没写" | 反问，不是人工理由 |
| 7 | "流程涉及多次返回 / 多次切换" | 只要 < 60 步且无跨端 / 跨账号即合规 |

> case 的本质 = "已知步骤 → 已知预期" 的因果链验证。把环境构造外移给人工预置 = 因果链断裂，case 退化为状态检查工具，丧失行为验证价值。

## 标题写法

`【人工】` 放在场景标签**前面**：

```
✅ 【人工】【正向】管理后台发布课程后 App 章节列表新增该课程入口
   → 类别 1（跨端：测前需在后台创建资源）

✅ 【人工】【兼容】iPhone 15 Pro 上 NFC 贴近后跳转支付页
   → 类别 6（硬件交互：NFC）

✅ 【人工】【正向】发布起 7 天后 NEW 徽标自动消失
   → 类别 5（真实环境敏感：真实时间窗口）

✅ 【正向】xxx                                              （默认 VLM 自动，无【人工】）
```

## 与两门铁律的咬合

```
                  写出 case
                      ↓
        ┌────────────────────────────┐
        │  ai-executable-rules.md     │  写法层：case 应不应该生成（写法对不对）
        └────────────────────────────┘
                      ↓
        ┌────────────────────────────┐
        │  execution-context-q'aire   │  信息层：信息够不够（7 类反问信号）
        └────────────────────────────┘
                      ↓
        ┌────────────────────────────┐
        │  manual-case-rules.md       │  路由层：VLM 能不能跑（step-first + 6 类边界 + 非人工理由清单）
        └────────────────────────────┘
                      ↓
                    输出
```

前两门管 case 自身质量；本文只决定 case 的执行方式。**任何一门铁律都不能因下一门让步。**
