# Spec 解析规则详细说明

本文档描述如何从 feature-list.md 格式的 Spec 中提取可测试要素。

---

## 1. 文档结构识别

### 1.1 模块边界

模块以 `## 模块 N：xxx` 或 `# 模块 N：xxx` 标题开始，到下一个同级模块标题结束。

提取信息：
- 模块编号（用于排序）
- 模块名称（用于 Level 1 输出）
- 模块优先级（从文档顶部的"模块总览"表格中读取 P0/P1/P2）

### 1.2 功能点边界

功能点以 `#### 功能点 X：xxx` 标题开始，到下一个 `####` 或 `###` 标题结束。

提取信息：
- 功能点字母编号（A/B/C...）
- 功能点名称（用于 Level 2 输出）

### 1.3 功能点内部结构

每个功能点内部包含以下固定段落（按出现顺序）：

| 段落标题 | 标识方式 | 提取用途 |
|---------|---------|---------|
| 交互说明 / 交互逻辑 | `**交互说明**` 或 `**交互逻辑**` | 主流程行为描述 |
| 业务规则 | `**业务规则**` | EARS 格式的规则条目 |
| 数据说明 | `**数据说明**`（可选） | 数据约束和依赖 |
| UI 设计意图 | `**UI 设计意图**`（可选） | 视觉/交互设计意图 |
| 异常处理 | `**异常处理**` | 异常场景和降级策略 |
| 埋点需求 | `**埋点需求**` | 跳过，不生成用例 |
| 验收项 | `**验收项**` | 验收骨架，作为用例来源之一 |

---

## 2. EARS 条目解析

### 2.1 识别模式

EARS 条目通常以 `- EARS-X（类型）：` 开头，或直接使用加粗的"**当**...**时**"格式。

解析为三元组：`(前置条件/触发条件, 动作/事件, 预期行为)`

**示例解析：**

原文：
```
EARS-E（事件驱动）：**当**用户变更任一级选择**时**，系统应立即联动刷新其后各级的可选项列表
```

解析结果：
```
前置条件：用户在教材选择弹窗中
触发条件：变更任一级选择
预期行为：其后各级的可选项列表立即联动刷新
```

### 2.2 交互说明中的隐式 EARS

交互说明段落中也使用 `**当**...**时**` 格式描述行为，应同等对待为可测试要素。

### 2.3 异常处理中的条件句

异常处理段落使用 `**如果**...**那么**` 格式，解析方式：

```
**如果**续播位置数据丢失**，那么**系统应从视频起始位置播放
```

解析为：
```
前置条件：续播位置数据丢失（模拟数据异常）
操作：点击进行中的视频卡片
预期结果：系统从视频起始位置播放，并提示用户可手动跳转
```

## 3. 验收项解析

验收项是 Spec 中最直接的测试用例来源，格式为：

```
- [ ] **当**...**时**，系统应...
  测试数据：xxx
```

解析规则：
1. checkbox 文字部分 → 拆解为"条件 + 预期行为"
2. `测试数据：` 行 → 纳入前置条件或操作步骤

**注意**：验收项通常覆盖不足，需要用 Phase 2 的六维度补充额外用例。验收项 ≠ 完整测试用例集。

---

## 4. Mermaid 流程图解析

从 Mermaid `flowchart TD` 代码块中提取：

1. **节点**：每个节点代表一个系统状态或用户动作
2. **边**：每条边代表一个状态转换或条件分支
3. **判断节点**（菱形 `{}`）：每个分支方向需要至少一条用例覆盖
4. **终端节点**（圆角 `([])`）：代表流程的入口或出口

**覆盖策略**：确保流程图中每条分支路径都被至少一条用例的操作步骤串联。

## 5. ASCII 示意图与状态流转解析

### 5.1 状态识别

从 ASCII 示意图标题中提取状态编号和名称：

```
【状态① 默认态 - 预习 Tab 激活】
【状态② 全部 Tab 激活态】
```

### 5.2 状态流转

从"状态流转"段落中提取转换规则：

```
① 默认态 --点击全部 Tab--> ② 全部激活态
```

解析为：
```
前置状态：默认态（预习 Tab 激活）
触发操作：点击全部 Tab
目标状态：全部 Tab 激活态
```

每条状态转换应有至少一条用例覆盖。

---

## 6. 跨功能点引用

当功能点描述中引用其他模块或功能点时（如"见模块 4"），记录依赖关系但不在当前模块重复生成该依赖模块的用例。仅在当前模块的用例中确保"跳转到模块 X"这一行为被验证。
